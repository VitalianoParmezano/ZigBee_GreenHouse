# LogicService

**LogicService** — автономний Python-мікросервіс для керування освітленням теплиць. Працює через MQTT-брокер, інтегрується із Zigbee2MQTT і керує контролерами (ESP32 / DALI), обчислюючи потрібну яскравість кожного каналу в реальному часі.

Головна архітектурна ідея — **перерахунок з нуля**. Сервіс не накопичує стан подій, а щотіку (раз на `tick_interval_sec`) заново рахує, що має світити зараз. Якщо сервер перезавантажився або зник зв'язок, на наступному тіку система сама повертається до правильного стану.

## Модель: зони, канали, режими

- **Зона** — один світильник (фізична група ламп).
- **Канал** — незалежний канал яскравості всередині зони (наприклад, різні спектри). Кількість зон і каналів задається в конфігу.

Кожен канал має **режим** та окремий прапорець **auto**:

| Параметр | Значення | Опис |
| :--- | :--- | :--- |
| `mode` | `manual` | Статична яскравість `brightness_user` (0–100 %). Застосовується одразу після `/set`. |
| `mode` | `timer` | Яскравість за розкладом `scenarios`. Розклад циклічний по добі. |
| `auto` | `0` / `1` | Не окремий режим, а **корекція поверх** `manual` або `timer`: віднімає світло, яке вже дає сонце (див. [Auto](#auto--daylight-harvesting)). |

Формат розкладу (JSON у полі `scenarios`):

```json
[
  {"time": "06:00", "brightness": 80},
  {"time": "20:00", "brightness": 30},
  {"time": "23:00", "brightness": 0}
]
```

Діє **остання мітка, час якої вже настав**. До першої мітки доби діє остання мітка «вчорашнього» дня, тому освітлення не скидається опівночі.

> `brightness_user` застосовується лише в режимі `manual`. У режимі `timer` значення зберігається, але на яскравість не впливає.

## Як рахується яскравість (загальний конвеєр)

Одиниця обробки — **зона**, а не канал. Це потрібно для PBD: ліміт потужності діє на суму всіх каналів світильника, тож обробляти канали по одному неможливо.

Одна й та сама функція `process_zone(zone)` викликається і тіком, і командою `/set`, тому жодна зміна не обходить PBD.

```
   +------------------+            +----------------------+
   |  tick (кожні N с)|            |  MQTT /set від UI    |
   |  для ВСІХ зон    |            |  для ОДНІЄЇ зони     |
   +--------+---------+            +-----------+----------+
            |                                  |
            +----------------+-----------------+
                             v
                    process_zone(zone)
                             |
        для кожного каналу зони:
                             |
              +--------------+---------------+
              |  1. mode: manual -> brightness_user
              |           timer  -> значення з розкладу
              +--------------+---------------+
                             |
                    auto = 1 ?  --yes-->  2. корекція за датчиком
                             |                  (Daylight Harvesting)
                             v
              цілі всіх каналів зони, напр. {1: 80, 2: 100, 3: 100}
                             |
                    power.enabled ?  --yes-->  3. PBD (ліміт ват на зону)
                             |
                             v
                  apply_brightness(zone, channel, %)
                             |
                             v
          zigbee2mqtt/Zone_X_Channel_Y/set
          {"state": "ON", "brightness": 38, "transition": 2}
```

Порядок важливий: **PBD завжди останній**, щоб гарантовано не перевищити потужність світильника, що б не вирахували попередні кроки.

## Auto — Daylight Harvesting

Мета: не вмикати штучне світло там, де вже достатньо природного. Базовий відсоток (з розкладу або ручний) переводиться в µmol/m²/s, від нього віднімається те, що реально показує датчик, а різниця знову конвертується у відсотки.

Параметр `max_umol` — скільки µmol/m²/s лампа каналу дає на **100 %**. Він зберігається в БД для кожного каналу окремо й задається через `LogicService/bridge/max_umol`.
  
<div align=center><img src=images/Auto_mode_logic.jpg></div>
  
Тобто розклад каже «50 %», але сонце вже дає частину потрібного, тому лампа вмикається лише на 38 %.

Ключові властивості:

- Працює і з `timer`, і з `manual`: розклад (або ручне значення) задає **бажану сумарну освітленість**, а auto визначає, скільки з неї докинути лампою.
- Якщо датчик показує більше, ніж потрібно, результат обрізається до 0 %. Auto лише **зменшує** штучне світло й ніколи не підвищує понад задане значення.
- Якщо `max_umol` каналу дорівнює 0 (значення за замовчуванням), auto завжди видає 0 %. Спершу задай `max_umol`.
- Датчик глобальний (один на теплицю), див. [Сенсор](#сенсор-освітленості).

## PBD — Power Balance Dynamic

Мета: **не перевищити максимальну потужність світильника у ватах**. Якщо сума запитаних яскравостей каналів зони «з'їдає» більше ват, ніж може видати світильник, PBD зменшує яскравість, віддаючи пріоритет за налаштуванням.

### Конфігурація

```yaml
power:
  enabled: true
  max_watts: 600        # ліміт потужності драйвера
  yield_channel: 1      # канал, який поступається (або null)
  channel_watts:        # скільки ват дає канал на 100 %
    1: 200
    2: 250
    3: 300
```

- Потужність каналу: `ват = % / 100 * channel_watts[канал]`.
- `yield_channel` — канал, який **втрачає яскравість першим**, коли інші зростають. Це не «захищений» канал, а навпаки, донор потужності.
- Канал, якого немає в `channel_watts`, вважається таким, що споживає 0 Вт.

### Алгоритм

```asci
Power Red = maxPower - Power Blue - Power White
```  
Реалізація алгоритму в `schedule_logic.py` у функції pbd_limit


### Приклади (`max_watts: 600`, `yield_channel: 1`, ват на 100 %: 200 / 250 / 300)

| Запит (ch1 / ch2 / ch3) | Сума | Результат (ch1 / ch2 / ch3) | Що відбулося |
| :--- | :--- | :--- | :--- |
| 20 / 100 / 100 | 590 Вт | 20 / 100 / 100 | Ліміт не перевищено |
| 80 / 100 / 100 | 710 Вт | 25 / 100 / 100 | Перебір 110 Вт повністю забрав ch1 |
| 100 / 100 / 100 | 750 Вт | 25 / 100 / 100 | Перебір 150 Вт забрав ch1 |

Якщо перебору не вистачає зрізати донора (наприклад, `max_watts: 400` і запит 100 / 100 / 100 = 750 Вт), то ch1 падає до 0 %, а ch2 і ch3 зменшуються пропорційно (≈ 72 %).

### Реакція на ручне керування

PBD спрацьовує й при `/set`: якщо користувач піднімає канал 2, `yield_channel` (канал 1) знижується в ту ж секунду, а не на наступному тіку.

Намір користувача (`brightness_user`) PBD ніколи не перезаписує. Тому коли навантаження зменшиться, канал-донор сам повернеться до бажаного значення.

## Потоки й синхронізація

У сервісі працюють два потоки, і обидва можуть вимагати перерахунку зони:

```
  Головний потік                        Потік paho (MQTT)
  --------------                        -----------------
  while True:                           _on_message
      _tick()  ----+                        |
      sleep(N)     |                        +--> _handle_set
                   |                                  |
                   |                          store.update(...)   (зберегти намір)
                   |                                  |
                   v                                  v
              process_zone(zone)  <------  on_set(zone)   (callback)

        [ threading.Lock: у process_zone одночасно лише один потік ]
```

- **`on_set`** — callback, який `SchedulerService` підставляє в `MqttState` при ініціалізації. Так `MqttState` може викликати розрахунок, нічого не знаючи про сервіс (без циклічних імпортів).
- **`Lock`** гарантує, що тік і `/set` не рахують одну зону одночасно й не розсилають суперечливі команди.
- `SchedulerService` і `MqttState` мають використовувати **один спільний `ChannelStore`** (один екземпляр, одне з'єднання з SQLite).

## Структура проєкту

### Кореневі файли
- **`main.py`** — точка входу. Запускає `SchedulerService` і перехоплює аварійні зупинки для зручного дебагу.
- **`config.yaml` / `config.example.yaml`** — налаштування: MQTT, кількість зон і каналів, інтервал тіку, логування, `power` (PBD).
- **`demo_resolve.py`** — CLI-утиліта для перевірки таймерного алгоритму без брокера.
- **`requirements.txt`** — залежності Python (`paho-mqtt`, `PyYAML`).
- **`Dockerfile` / `.dockerignore`** — пакування в контейнер із коректним часовим поясом (`tzdata`).

### `scheduler/`
- **`config.py`** — завантажує `config.yaml` і перетворює його на типізовані об'єкти `Settings` / `PowerSettings`.
- **`service.py`** — оркестратор. Цикл `_tick()` і `process_zone(zone)`: збирає цілі каналів зони, застосовує Auto та PBD, відправляє команди.
- **`mqtt_state.py`** — MQTT-шар: підключення, підписки, обробка `/set` і `/get`, пересилання показів датчика, публікація команд у `zigbee2mqtt/`.
- **`store.py`** — потокобезпечне сховище SQLite: `channel_config` (режим, розклад, `brightness_user`, `auto`) і `lamp_config` (`max_umol` по каналах). Єдине джерело правди для налаштувань.
- **`schedule_logic.py`** — чиста логіка без мережі та БД: парсинг розкладу, цільовий відсоток на поточну хвилину, корекція Auto (`auto_correction_resolve`), обмеження PBD (`pbd_limit`). Легко тестується окремо.

## MQTT-контракт

Уся взаємодія з UI й датчиками відбувається в просторі `LogicService/*`.

| Топік | Напрямок | Призначення |
| :--- | :--- | :--- |
| `LogicService/Zone_X_Channel_Y/set` | **ВХІД** | Зміна налаштувань каналу. Підтримувані поля: `mode`, `scenarios`, `brightness_user`, `auto`. Невідомі ключі ігноруються. |
| `LogicService/Zone_X_Channel_Y/get` | **ВХІД / ВИХІД** | Запит стану. Порожній payload — усі поля; `["mode","auto"]` або `{"mode":1}` — лише перелічені. Відповідь іде в той самий топік. |
| `LogicService/Zone_X_Channel_Y` | **ВИХІД** | Retained broadcast повного стану каналу після кожної зміни (зручно для UI). |
| `LogicService/bridge/sensor` | **ВХІД** | Показник датчика освітленості: `{"lux": 1554}`. Використовується Auto. |
| `LogicService/bridge/max_umol` | **ВХІД / ВИХІД** | `max_umol` ламп по каналах: `{"max_umol_channel1": 250.0, "max_umol_channel2": 150.0}`. Retained-копія публікується при старті; зміна перераховує вплив на Auto. |
| `LogicService/bridge/power` | **ВИХІД** | Retained: параметри PBD з `config.yaml`, напр. `{"enabled": true, "max_watts": 600, "channel_watts": {"1": 200, "2": 250, "3": 300}, "yield_channel": 1}`. Публікується при кожному підключенні до брокера. Потрібен UI для розрахунку µmol (див. [Розрахунок µmol у UI](#розрахунок-µmol-у-ui)); сам сервіс на нього не підписаний. |
| `LogicService/bridge/info` | **ВИХІД** | Retained: службова інформація про сервіс (dry_run, зони, канали тощо). |
| `zigbee2mqtt/Zone_X_Channel_Y/set` | **ВИХІД** | Реальна команда пристрою: `{"state": "ON", "brightness": 38, "transition": 2}`. |

Приклад `/set`:

```json
{"mode": "timer", "auto": 1, "scenarios": [{"time": "06:00", "brightness": 80}]}
```

## Сенсор освітленості

LogicService виконує роль **пересилача**. Він слухає всі пристрої `zigbee2mqtt/+` і, коли знаходить повідомлення з ключем `illuminance`, публікує значення в `LogicService/bridge/sensor` у форматі `{"lux": 123}`.

- Зараз показ датчика **один на всю теплицю**. Усі зони з увімкненим Auto орієнтуються на нього.
- Для кількох сенсорів потрібно або усереднювати значення в `bridge/sensor`, або розширювати топіки до `bridge/sensor/zoneN` і прив'язувати сенсор до зони. Це окрема задача.
- Конвертація lux → µmol/m²/s поки що через емпіричний коефіцієнт `lux / 69`.

## Розрахунок µmol у UI

Картка `greenhouse-zone-card` (Home Assistant) рахує µmol сама UI лише читає дані які необхідні для розрахунку мікромолей з MQTT.

- **Ручний режим:** µmol каналу = `brightness_real × max_umol / 100`, загальна сума — сума по каналах. `brightness_real` береться з retained-топіка `LogicService/Zone_X_Channel_Y` і вже враховує Auto та PBD, тому цифра збігається з тим, що реально світить.
- **Таймер:** сума рядка розкладу = Σ `% × max_umol / 100`. Відсотки спершу проходять через копію `pbd_limit` (`pbdLimit` у `greenhouse-zone-card.js`), параметри якої картка бере з `LogicService/bridge/power`, а `max_umol` — з `LogicService/bridge/max_umol`. Auto у розкладі не враховується: він залежить від показу датчика в момент виконання, тож сума показується «до Auto».

> Логіка PBD існує у двох місцях: `schedule_logic.pbd_limit` (Python) і `pbdLimit` (JS). Змінюючи одну, змінюй і другу. На яскравість ламп це не впливає, лише на попередній розрахунок µmol у таймері.

## Конфігурація та запуск

Перед запуском створи `config.yaml` (приклад нижче) поруч із `main.py`. Інший шлях можна передати аргументом: `python main.py my-config.yaml`.

```yaml
mqtt:
  host: mosquitto
  port: 1883
  user: ""
  password: ""
  base_topic: zigbee2mqtt

scheduler:
  zones: 8
  channels_per_zone: 3
  tick_interval_sec: 30
  # true = сервіс лише логує, що б відправив, і нічого не публікує в /set
  dry_run: false
  # Час переходу між поточною та цільовою яскравістю, у секундах (цілі числа)
  transition: 2

# PBD: обмеження потужності світильника
power:
  enabled: true
  max_watts: 600    # Потужність драйвера
  yield_channel: 1  # Номер каналу що поступається
  channel_watts:    # Потужність каналів
    1: 200
    2: 250
    3: 300

logging:
  # DEBUG - показує кожен канал на кожному тіку; INFO - лише реальні події
  level: INFO
  # Тека файлових логів (відносно кореня проєкту)
  dir: logs
  # Скільки днів логів зберігати; старіші видаляються автоматично щоночі
  retention_days: 7
```

## Відомі обмеження

- Коефіцієнт `lux → µmol` (`69`) зашитий у коді й однаковий для всіх типів світла.
- Датчик один на всю теплицю (див. [Сенсор](#сенсор-освітленості)).
- Для Auto обов'язково треба задати `max_umol` кожного каналу, інакше результат завжди 0 %.
